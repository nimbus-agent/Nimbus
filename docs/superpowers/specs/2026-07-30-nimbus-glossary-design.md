> Phase 7 Wave 5 ("Implicit Knowledge Surfaces"). Second member of the implicit-knowledge
> triad after `nimbus why` (shipped 2026-07-24, #820).

> Roadmap rows: `docs/roadmap.md` — S1 "Remaining" (~line 913), Wave 5 bullet (~line 1071),
> Wave 5 acceptance criterion (~line 1105).

## 1. What it is

A tenth built-in read-only agent that turns terminology the team already uses — but has never
written down — into a queryable glossary, extracted entirely from the local index.

```
nimbus glossary            # terms, sorted by frequency
nimbus glossary CDR        # the team's consolidated definition of CDR
nimbus glossary --json     # typed findings
nimbus glossary --refresh  # force an extraction pass now
nimbus glossary --rebuild  # wipe and re-mine from scratch
```

The onboarding story it serves: a new engineer asks "what does CDR mean here?" and gets the
team's actual usage — with first-seen / last-seen dates and the threads that define it — rather
than Wikipedia's answer.

**No new connectors, no new infrastructure, no live API call.** Every input is already indexed.

## 2. Why this shape

Glossary differs from every existing built-in agent in one structural way: it **materializes
state**. `why`, `expert`, `catchup`, `impact`, `ghost`, `conflicts`, `huddle`, `janitor` and
`preflight` all compute on demand and persist nothing. Glossary maintains a `glossary_term`
item type, refreshed by a periodic pass.

That difference drives the whole design, and it splits the feature into two paths that must not
be conflated:

| | Extraction (write path) | Agent (read path) |
| --- | --- | --- |
| Trigger | debounced, after a successful connector sync | user command / IPC call |
| Cost | bounded local-LLM calls | pure SQLite reads |
| Lives in | `packages/gateway/src/glossary/` | `packages/gateway/src/agents/glossary.ts` |

Four decisions were taken at design time, each with the rejected alternatives recorded:

1. **Materialize + wire the scheduler now** (vs. lazy-refresh-only, vs. ephemeral). The roadmap
   says "generated by a periodic agent", and the scheduler seam already exists — see §7.
2. **Deterministic mining + LLM consolidate/veto** (vs. LLM-driven extraction, vs. no LLM). Keeps
   LLM cost at O(new terms) instead of O(index), keeps mining unit-testable, and matches the
   roadmap's "cheap; uses local LLM for the consolidation step".
3. **Ranked cap per pass, resume next pass** (vs. unbounded frequency floor, vs. a hard glossary
   size ceiling). Bounds worst-case pass latency without ever silently losing a term.
4. **V45 table + item projection** (vs. table-only, vs. no migration). The table is the SSoT
   including pending/vetoed working state; only consolidated terms reach the searchable index.

## 3. Module layout

```
packages/gateway/src/glossary/
  glossary-types.ts          GlossaryTerm, GlossaryCandidate, GlossaryBrief, GlossaryFinding
  term-mining.ts             pure: text -> candidate surface forms (5 regex families)
  term-normalize.ts          pure: surface form -> term_key (casefold, de-pluralize, strip ticks)
  stopwords.ts               shipped common-English + common-tech baseline
  term-scoring.ts            pure: (docFreq, serviceSpread, form) -> score
  near-miss.ts               pure: acronym<->expansion synonyms + edit-distance near-misses
  glossary-source-types.ts   GLOSSARY_SOURCE_TYPES — which service:type keys feed mining
  glossary-store.ts          V45 reads/writes (every write via dbRun/dbExec — I14)
  glossary-consolidate.ts    local-LLM call + JSON parse + veto handling
  glossary-project.ts        consolidated row -> nimbus:glossary_term item upsert
  glossary-extract.ts        the pass orchestrator
  glossary-refresh.ts        debounced post-sync trigger

packages/gateway/src/agents/glossary.ts    runGlossary + emitGlossaryBrief
packages/cli/src/commands/glossary.ts      CLI entry point
```

The five pure modules exist as separate files for a reason beyond tidiness: new source files carry
a ≥80% line **and branch** coverage floor, and pure functions cover to ~100% cheaply. Burying the
regex families inside the pass orchestrator would make that floor expensive to reach.

## 4. Schema (V45)

Two tables. `glossary_term` is the SSoT; `glossary_pass_state` is a single-row watermark.

```sql
CREATE TABLE IF NOT EXISTS glossary_term (
  term_key          TEXT PRIMARY KEY,       -- normalized: casefold + singular
  display_term      TEXT NOT NULL,          -- most-frequent observed surface form
  status            TEXT NOT NULL CHECK(status IN ('pending','consolidated','vetoed')),
  definition        TEXT,                   -- NULL until consolidated
  definition_source TEXT CHECK(definition_source IN ('llm','snippet')),
  doc_freq          INTEGER NOT NULL DEFAULT 0,
  service_spread    INTEGER NOT NULL DEFAULT 0,
  score             REAL    NOT NULL DEFAULT 0,
  first_seen_at     INTEGER NOT NULL,       -- MIN(item.modified_at) over citing items
  last_seen_at      INTEGER NOT NULL,       -- MAX(item.modified_at) over citing items
  top_sources       TEXT NOT NULL DEFAULT '[]',  -- JSON, max 5
  synonyms          TEXT NOT NULL DEFAULT '[]',  -- JSON string[]
  near_misses       TEXT NOT NULL DEFAULT '[]',  -- JSON string[]
  consolidated_at   INTEGER,
  updated_at        INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_glossary_term_status_score
  ON glossary_term(status, score DESC);
CREATE INDEX IF NOT EXISTS idx_glossary_term_display
  ON glossary_term(display_term);

CREATE TABLE IF NOT EXISTS glossary_pass_state (
  id            INTEGER PRIMARY KEY CHECK(id = 1),
  watermark_ms  INTEGER NOT NULL DEFAULT 0,   -- max item.modified_at scanned
  last_pass_at  INTEGER,
  last_pass_new INTEGER NOT NULL DEFAULT 0,
  scanned_items INTEGER NOT NULL DEFAULT 0
);
```

`first_seen_at` / `last_seen_at` are **content** dates — when the team first and last *used* the
term — not row timestamps. That is what the roadmap's onboarding story needs, and it is why they
are recomputed rather than stamped on insert.

Registered in `migrations/runner.ts` as
`simpleStep(44, 45, "glossary_term + glossary_pass_state (implicit-knowledge glossary v45)", GLOSSARY_V45_SQL)`,
with SQL in `index/glossary-v45-sql.ts` — matching the V41/V43/V44 precedent.

## 5. The extraction pass

### 5.1 Mining discovers terms; FTS recomputes statistics

The load-bearing decision. The incremental scan reads only items with
`modified_at > watermark_ms`, but it **never increments a counter**. For every candidate it
touches, exact global statistics are recomputed from the existing `item_fts` index:

```sql
SELECT COUNT(*)                  AS doc_freq,
       COUNT(DISTINCT i.service) AS service_spread,
       MIN(i.modified_at)        AS first_seen,
       MAX(i.modified_at)        AS last_seen
FROM item_fts f
JOIN item i ON i.rowid = f.rowid
WHERE item_fts MATCH ? AND i.type IN (...)
```

Accumulated counters drift permanently the first time an item is edited, re-synced, or deleted —
and the drift is invisible, because nothing ever recomputes the truth. Recomputed statistics are
idempotent: running the pass twice, or ten times, converges on identical numbers. A
**run-pass-twice-converges** integration test locks this in (§10).

The same query yields `top_sources` — the 5 highest-ranked citing items by FTS rank blended with
recency, stored as `[{itemId, title, url, service, modifiedAt}]`.

### 5.2 Sequence

1. Read `watermark_ms`; select source-scoped items with `modified_at > watermark_ms`.
2. Mine candidate surface forms from `title || ' ' || body_preview`.
3. Normalize to `term_key`; drop stopwords.
4. Recompute statistics per candidate via §5.1.
5. Drop candidates with `doc_freq < min_doc_freq` (default 3).
6. Score; upsert as `status='pending'` (never downgrading an existing `consolidated` row).
7. Take the top `max_new_terms_per_pass` (default 25) unconsolidated rows by score.
8. Consolidate each (§5.4); `vetoed` rows stop here.
9. Project consolidated rows into `item` (§6).
10. Advance `watermark_ms` to the max `modified_at` scanned; record pass stats.

`doc_freq >= 3` is not arbitrary: the Wave 5 acceptance criterion requires a term to be evidenced
"across at least 3 source threads".

### 5.3 Candidate families and scoring

`term-mining.ts` emits candidates from five families, each tagged with its form:

| Family | Example | Form boost |
| --- | --- | --- |
| Acronym (2–6 uppercase, optional plural `s`) | `CDR`, `SLOs` | 1.3 |
| Backticked / code-fenced token | `` `shard_key` `` | 1.2 |
| PascalCase / camelCase identifier | `RetryBudget` | 1.1 |
| Hyphenated compound | `write-behind` | 1.05 |
| Capitalized multi-word phrase (2–4 words) | `Shadow Traffic` | 1.0 |

```
score = log1p(doc_freq) * (1 + 0.5 * (service_spread - 1)) * formBoost
```

Spread across services is weighted deliberately: a term appearing in both Slack *and* Jira is far
more likely to be real team vocabulary than one appearing 40 times in a single noisy channel.

`stopwords.ts` ships a static baseline (common English + ubiquitous tech terms — `API`, `HTTP`,
`JSON`, `TODO`, `PR`, `CI`) so the glossary does not fill with vocabulary that carries no
team-specific meaning.

### 5.4 Consolidation

Per term, one local-LLM call over its top source snippets. The snippets are third-party indexed
content flowing into the model, so they are wrapped with `wrapToolOutput` — this is precisely the
prompt-injection seam invariant **I11** exists for.

Expected response:

```json
{ "isDomainTerm": true, "definition": "...", "alsoKnownAs": ["..."] }
```

- `isDomainTerm: false` → `status='vetoed'`. Sticky; never re-asked. `--rebuild` is the escape
  hatch if a veto was wrong.
- Malformed or empty response → the row stays `pending` and is retried next pass. It is not
  vetoed: an unparseable response is a model failure, not a judgment about the term.
- `alsoKnownAs` merges into `synonyms` alongside the deterministic acronym↔expansion detection
  in `near-miss.ts` (which recognizes the `Change Data Record (CDR)` pattern in source text).
- `near_misses` are computed deterministically: other known terms within edit distance ≤ 2, or
  sharing a normalized stem.

### 5.5 Degradation without an LLM

Zero-config onboarding (#887) demoted the LLM to optional, so a fresh machine may have none.
Glossary must not be dead there.

- **No LLM configured** → the term is consolidated with `definition_source='snippet'`: the
  verbatim sentence containing the term, drawn from its highest-ranked source. Honest,
  attributable, zero-cost. No veto is possible in this mode.
- **LLM configured later** → the next pass re-queues `snippet`-sourced terms for upgrade to
  `definition_source='llm'`. No rebuild, no user action.
- The brief always labels which mode produced a definition, so a raw quote is never mistaken for
  a synthesized definition.

This keeps the Wave 5 acceptance criterion honest — the *consolidated* definition is generated by
the local LLM with zero live API calls — while leaving the feature useful on an LLM-less install.

## 6. Item projection

Only `status='consolidated'` rows reach the searchable index:

| Column | Value |
| --- | --- |
| `service` | `nimbus` |
| `type` | `glossary_term` |
| `external_id` | `glossary:<term_key>` |
| `title` | `display_term` |
| `body_preview` | `definition` |
| `metadata` | `{definitions, synonyms, nearMisses, topSources, firstSeenAt, lastSeenAt, docFreq, definitionSource, generatedAt}` |

Written via `upsertIndexedItem` (the `research_brief` precedent in `briefs/brief-save.ts`).
`nimbus:glossary_term` joins `PROSE_HEAVY_TYPES` in `embedding/routing.ts` (22 → 23 entries).

The payoff is that `nimbus ask "what does CDR mean here?"` retrieves the glossary through ordinary
FTS + vector search, with **no glossary-specific code in the ask path**.

Consistency rule: a term leaving `consolidated` (via `--rebuild`, or a veto on re-consolidation)
has its projected item row **deleted**. A stale definition surfacing in search after the term was
rejected would be worse than no glossary at all.

## 7. Trigger and configuration

`glossary-refresh.ts` hangs off the existing `onConnectorSyncSuccess` callback in
`platform/assemble.ts` (~line 435) — the same seam `evaluateWatchersAfterSync` already uses. No
new timer, no new lifecycle object. Calls are debounced (default 60 s) so a burst of connector
syncs coalesces into a single pass, and the pass is skipped entirely when one is already running.

```toml
[glossary]
enabled = true              # local-only, no egress
max_new_terms_per_pass = 25
min_doc_freq = 3
debounce_ms = 60000
```

**Default-on**, unlike `[briefs]`. `[briefs]` is default-off because it opens an HTTP write
surface; glossary opens nothing — it reads the local index and writes local rows. Its only cost is
bounded local-LLM time, already capped at 25 calls per pass.

`nimbus glossary --refresh` forces a pass immediately; `--rebuild` truncates both tables, deletes
projected items, and re-mines from `watermark_ms = 0`.

## 8. The agent (read path)

`runGlossary` fans out four `AgentCoordinator` lanes. Each lane reads a different table, so the
parallelism is real rather than ceremonial:

| Mode | Lane 1 | Lane 2 | Lane 3 | Lane 4 |
| --- | --- | --- | --- | --- |
| `glossary <term>` | term row + definition | hydrate `top_sources` → join `item` | synonyms | near-misses |
| `glossary` (no arg) | ranked consolidated list | coverage stats | gap notes | — |

Per the agent shape invariant: read-only, HITL-free, parallel, and emitting
`glossary.briefReady { sessionId, brief, findings }` via `emitBriefWithSynthesis`.

**Miss path.** An unknown term does not return an empty brief — it returns near-misses as "did you
mean", which is the single most likely first interaction for the new-engineer use case the feature
exists to serve.

**Gap notes** reuse `_lib/gap-notes.ts`, covering: empty index; glossary never run; a pass ran but
every candidate fell below `min_doc_freq`; and `pending > 0` (fill-in still in progress), so a
partially-built glossary explains itself rather than looking broken.

`GlossaryBrief` joins the `AnyBrief` union in `_lib/findings.ts`, the `SynthInput` union and
`deterministicRender` / `toolNameFor` switches in `_lib/synthesize.ts`, and gains
`renderGlossary()` in `_lib/render.ts` — so the deterministic fallback and the
`_Rendered deterministically_` footer come for free.

## 9. IPC and CLI

- **IPC:** one method, `agents.glossary { term?, limit?, refresh?, rebuild? }` → `{ sessionId }`,
  followed by `glossary.briefReady` / `glossary.briefError`.
- **Tauri:** `agents.glossary` added to `ALLOWED_METHODS` (**I7**) — 101 → 102, including the
  count assertion at `gateway_bridge.rs:518`. Read-only and non-RCE, so exposure is safe.
- **CLI:** `packages/cli/src/commands/glossary.ts`, registered in `packages/cli/src/index.ts`,
  driven by the shared `runAgentBriefCli` helper in `_agent-brief-cli.ts`. Respects `NO_COLOR`.
  Exit codes match the sibling agents: 1 = gateway not running, 2 = agent error.

The CLI cannot import gateway source (IPC-only rule) and `@nimbus-dev/sdk` has no glossary types,
so the command carries a local structural `isGlossaryBriefLike` guard — the same stand-in
`why.ts` uses, with the same comment pointing at a future SDK promotion.

## 11. Security invariants

**No new invariant.** Glossary is read-only, performs no egress, declares no HITL action type,
adds no HTTP route, and adds no connector. Existing invariants it must satisfy:

- **I14 / D12** — every V45 write through `dbRun` / `dbExec` / `dbStmtRun`. The static audit fails
  the preflight otherwise.
- **I11** — `wrapToolOutput` around source snippets fed to the consolidation LLM.
- **I7** — the `ALLOWED_METHODS` addition above.
- **I29 / D22** — untouched. Glossary never reaches `connectors.dispatch`, so it appends no
  `egress_ledger` rows. That is correct, not an omission: nothing leaves the machine.

## 12. Known limits (stated, not discovered later)

- **512-character ceiling.** `index/item-store.ts` clips `body_preview` to 512 chars, so mining
  sees title + 512 chars per item. A term defined only deep inside a long Confluence page is found
  only if it also appears early somewhere else. Acceptable — jargon repeats by nature — but it is
  the recall ceiling.
- **Lowercase jargon is out of reach.** Deterministic mining cannot see "the funnel" or "shipping
  mode" as terms. LLM-driven extraction would catch them at O(index) cost; that trade was
  considered and rejected. Revisit only with evidence from real usage.
- **Email and calendar are excluded** from `GLOSSARY_SOURCE_TYPES`. The roadmap does not list
  them, and mining a personal inbox into a team glossary is not a posture to adopt silently.
- **Vetoes are sticky.** `--rebuild` is the only reset.
- **Single-user scope.** Federation makes the glossary richer (Phase 6 primitives exist), but no
  federated fan-out ships in this slice.
