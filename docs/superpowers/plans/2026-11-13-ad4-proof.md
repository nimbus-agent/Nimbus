## Design decisions

**D-1 What "door" and "proposer" mean in a row.** Door: the gateway-set entry the action came through, `"agent"` here. Proposer: `{ door, captureId, label, labelSource }`, where `captureId` is the gateway's own id (`cap_` plus 32 hex, `mcp-sink/capture-id.ts`) and `label` is the client's own text. Every value is copied from the stored capture row by `agentProposerOf`, the only writer (D49(c)).

**D-2 What is hashed, and what happens to existing rows.** Neither formula changes. An audit row hashes its own `action_json` (`db/audit-chain.ts:17-25`), so a new row with more fields hashes over them and an old row verifies as before. An egress row hashes its own `source_id` (`egress/egress-ledger.ts:27-31`), and the verifier recomputes from stored values (`egress/egress-verify.ts:151-160`). `listEgress` order and `digestEgressWindow` are untouched, so a receipt already issued recomputes to the same digest.

**D-3 The label can never break a ledger or pass as verified.** It goes only into JSON (encoded) in the audit row and into the unhashed `payload_summary`. It never goes into `source_id`: that field is joined with `|` in the hash input, so a label holding `|` could shift field boundaries. `source_id` holds only the capture id, checked against `^cap_[0-9a-f]{32}$` (a failure throws before either row is written, and the action is not dispatched). In `payload_summary` the label is cut to 48 units so some payload stays inside the 256. The proposer projection stays first in the audit row and is at most about 1,100 units in the worst case (100 units of lone surrogates), well inside 4,096. Every output prints the label through `escapeUnverifiedLine` (`engine/proposer-block.ts:40-42`), in quotes, after the word `UNVERIFIED`; the JSON reply carries `labelsVerified: false`.

**D-4 Sub-steps.** The executor derives one attribution per run from the parent action and puts it in the scope of its before-state reads, prepare read and discard. Those rows carry `onBehalfOf` in the audit JSON and the parent's `source_id` in the ledger. An action that is not agent-origin produces byte-identical rows to today's.

**D-5 No migration.** `idx_egress_ledger_source (source_type, source_id)` exists (`index/egress-ledger-v44-sql.ts:26`) and serves `source_type = 'task' AND source_id >= 'agent:' AND source_id < 'agent;'`. The audit side is a windowed scan with a row cap; `audit_log` has no timestamp index, and the chain verify already reads the whole table. Alternative, not recommended: V98 `audit_log.capture_id` plus an index. It would be an unhashed column, would need a field on `AuditSink`, and buys speed only. If chosen, V98 is the next free number at V97; re-check with `ls packages/gateway/src/index/migrations/runner-v*.test.ts`, the same listing on `origin/main` after `git fetch`, and `gh pr list --state open` searched for `V98`, then follow `nimbus-db-migrations` (forward-only, re-runnable, a fresh and an upgrade test).

**D-6 Reading rows.** Lifecycle rows are parsed as JSON. Executor rows are matched by a regex anchored at the start of the row (optional digest keys, then `"action":{"type":…,"proposer":{"door":"agent","captureId":…`), because a cut row does not parse and because an unanchored match could be forged by an input object that contains the same text. Parsing is in TypeScript, never `json_extract` (`standing/approval-learning.ts:19-23`; the regex precedent is `ipc/standing-rpc.ts:430-443`).

**D-7 The completeness check, exactly.** For every capture with a `capture.action.accept` row in the window that carries `labelSource` (written by this version or later):
- E1: the multiset of (action type, `hitl_status`) over its audit gate rows (the proposer row and its `onBehalfOf` rows) equals the multiset of (`method`, `hitl_status`) over egress rows with `source_id = agent:<id>`; `result_status` is `blocked` exactly when the status is `rejected`.
- E2: at most one approved proposer row and one authorized egress row of the write's type.
- L1: one accept, then exactly one `capture.action.outcome`; an accept with no outcome older than the newest boot marker is a mismatch (the boot reconcile runs before the marker, `platform/assemble.ts:3637`, `:3782`).
- L2: `executed` needs one approved proposer row; `rejected` needs none.
- L3: the proposer row's label equals the submit row's, after the same redaction.
- An egress `agent:` row whose capture has no audit gate row is a mismatch.

Any mismatch, an unreadable row, a cut scan, a failed audit or egress chain verify, or `task` coverage of `none` gives `indeterminate` and exit 1. Not checked, and reported as counts: proposals accepted before this version, and audit rows at or before the newest prune tombstone's timestamp. What the ledgers cannot show: an action that never reached the executor (I29 and D22's claim, not this report's), the newest rows removed from both chains together, whether the label is true, whether the remote service applied the write (the egress row precedes the call), and anything an agent did with its own credentials.

**D-8 `nimbus prove --by-proposer [--since <dur>] [--proposer <label>] [--json]`.** It runs no query; a positional argument is a usage error. It calls `audit.proveByProposer`. Groups are keyed by (label, labelSource); a null label is `(no label)`. Per group: proposed, refused at submit, approved (audit), declined (`capture.reject` plus `rejected` outcomes), executed, failed, expired, waiting, dispatches (egress), and connections under OD-2(b). `--proposer` matches the stored label or its escaped form. The header states that labels are the client's own claim. An auditor can conclude: these proposals were recorded, the owner's gate approved this many, and both ledgers agree. An auditor cannot conclude which program sent them.

**D-9 Audit view.** `nimbus audit --door <agent|model|workflow> [--proposer <label>] [--since <dur>] [--limit N] [--json]` calls `audit.listByDoor` and prints timestamp, action, status, capture id, the UNVERIFIED label and the reason. `--proposer` implies `--door agent`. An `nimbus approvals` history view is not built; `captures list` already shows finished actions.

**D-10 IPC exposure.** Both methods are in the `audit` namespace (LAN-forbidden as a whole), are not on the Tauri allowlist, and answer only a connection that declared `cli` or `ui`, the rule AD2 set for new owner methods (`ipc/approvals-rpc.ts:53-60`). The CLI commands call `declareCliClientKind` first. Reviewer decision R-1.
