## Size and split

The slice row holds two different kinds of work. The agent grant, hash, display and describe change who may reach a user MCP tool and touch `mcp-sink/`, `ipc/`, `connectors/connector-writes/` and the executor's prompt. The write grants change what the sandbox lets third-party code do on each OS and touch `platform/sandbox/`, `connectors/lazy-mesh/`, the registration resolver and a migration. The spec allows the split (`:529`: "If review wants it separate it becomes AD5b"). The two parts share one seam only: the per-call display has a `write:` line. AD5a renders that line from a field that is always empty, so AD5b fills it without touching the prompt code. Each part amends different invariants (AD5a: I42, I11, I28, I58, D49; AD5b: I15, D10), so the triple rule is satisfied inside each PR. If the owner prefers one PR, the AD5b tasks follow AD5a's Task 14 and the migration number is unchanged.

Inside AD5a the commit order keeps `audit:invariants` and `security-invariants.test.ts` green at every commit: commits 1 and 2 add the read side, the act side and the display while no code can yet write an agent approval for an `mcp_*` service, so production behaviour is unchanged except the legacy flag; commit 3 is the flip and describe together (the enable handler, the I42 and I11 text, the D49 clauses, the describe wiring for `mcp_*` and their tests); commit 4 is the CLI, e2e and docs.

**What changes only for an owner who opts in** (approves a tool by name): that tool moves to the `approved` basis. It no longer needs `--model`. Its listed definition is hashed and checked at submit, at approval and after the owner's answer. It can be approved only through `approvals.approve` by a person (rule 4d). A changed definition suspends it. The agent can read its description and schema through `describe_actions`. An agent's submit or describe for it can start the server.

**What newly works:** a server registered without `--model` can be reached by outside agents for the tools the owner approved by name.

**What does not change for anyone:** every `mcp_*` call still needs the local owner's approval at the executor gate, is never delegated, and dispatches only the gateway-derived key for its own type. Extensions (`ext_*`) stay unproposable.

## Owner decisions

**Settled 2026-11-14.** The owner chose the recommended option of each: **OR-AD-22** (OD-1) the agent grant for a user MCP server is the owner's approval of named tools with the existing command, `nimbus connector writes enable mcp_<id> --door agent --approve <tool>...`, stored in the existing V97 door table; no flag at registration and no migration. **OR-AD-23** (OD-3) for an `mcp_*` service `--approve` is required and takes exact tool names only; with no `--approve` the command lists the server's tools with their hash prefixes and exits without a prompt. **OR-AD-24** (OD-4) no typed confirmation for an agent's `mcp_*` call: a person's plain answer on a declared `cli` or `ui` connection, never `--yes` or a script. **OR-AD-25** (OD-5) `describe_actions` describes a user-MCP tool from a live listing, and may start the server, only for a tool the owner approved for agents that is not suspended, within the existing per-call and rate bounds. **OR-AD-26** (OD-2) the user-MCP legacy case may be removed only after a release containing AD5a has been published; if AD3b merges sooner it leaves this case for a follow-up one release later. The options are kept below as the record.

These are design and limitation choices the spec and OR-AD-1 to OR-AD-21 do not settle. Each lets third-party code be driven further by outside agents, so each is the owner's.

- **OD-1 What the agent grant is, and where it is recorded.** (a) There is no flag at registration. The grant is the owner's approval of named tools: `nimbus connector writes enable mcp_<id> --door agent --approve <tool>...`, recorded as rows of the existing V97 table (`service = mcp_<id>`, `door = 'agent'`, `tool_id = <tool>`). No migration. It is OR-AD-2's own command. One command ends the deprecation warning. (b) `connector add --mcp ... --agent` records a server-level bit in a new column (`agent_access`, V98) that the per-tool enable then requires. An owner with a server already registered must remove and re-add it, which deletes its indexed items and sandbox directory. (c) `--agent` at registration is CLI sugar that runs the enable right after the registration, as a second prompt. Recommendation: (a). The flag name `--agent` already means the kit label on `nimbus mcp-server`. This plan is written for (a). Under (b): V98 is the next free number; re-check with `git fetch origin && git show origin/main:packages/gateway/src/index/local-index.ts | grep CURRENT_SCHEMA_VERSION`, `ls packages/gateway/src/index/migrations/runner-v*.test.ts`, and `gh pr list --state open --search "V98"`, then follow `nimbus-db-migrations`.
- **OD-2 When the user-MCP deprecation window ends.** The warning for a user-MCP proposal first exists in the release that contains AD5a, because before it the owner had no way to approve a tool by name. (a) The enforcing slice may delete the user-MCP legacy case only after a release containing AD5a has been published (D-AD-15's rule applied to this case). If AD3b merges before that, it leaves the user-MCP legacy case and a small follow-up deletes it one release later. (b) AD3b deletes it whenever AD3b merges; an owner may then meet the refusal with no prior warning. Recommendation: (a), because OR-AD-9 promises one release of warning.
- **OD-3 How tools are named in the approval.** (a) For an `mcp_*` service `--approve` is required and takes exact tool names only. With no `--approve` the command prints the server's tools with their hash prefixes and exits without a prompt. (b) The first-party rule: no `--approve` approves every listed tool, and a prefix `name*` is allowed (`agent-writes.ts:109-128`, `:189-206`). Recommendation: (a). A third-party server chooses its own tool names and can add tools at any time; exact names keep "approved by name" literal. Stated limit under (a): a server with many tools needs a long command.
- **OD-4 Typed confirmation for an agent's `mcp_*` call.** (a) None, as the spec says (`:518`): a person's plain answer on a declared `cli` or `ui` connection, no `--yes`. (b) The owner types the tool name for every agent-proposed `mcp_*` call. (c) Typed only when the server has a `--net` or (AD5b) `--write` grant. Recommendation: (a). The confirm text of D41 is computed from a write row's target, and a user MCP tool has no row and no target the gateway understands. Stated limit: approving third-party code for an agent is one keystroke by a person, as approving it for the model is today.
- **OD-5 An agent's read can start third-party code.** OR-AD-17 deferred describing `mcp_*` tools so that "an agent's read never starts owner-registered third-party code". (a) Describe an approved tool from a live listing. The server starts only when the call names a tool the owner approved for agents that is not suspended, at most 3 services a call (`mcp-sink/capture-describe.ts:38`) and `4 x max_per_hour` calls an hour on the describe window (`:42`). This adds no new class of start: a submit for an approved tool already lists at step 5c. (b) Store the approved description and schema at enable and describe from the copy: needs a migration and can describe a definition the live check would refuse. (c) Keep `mcp_*` undescribed. Recommendation: (a).

Process calls made here: the two-PR split; I42 carries the user-MCP rule and I58 stays first-party (D-11).

## Design decisions

**D-1 Scope.** `mcp_*` only. The spec's § 7.5 speaks only of `mcp_*` types and of `userMcpToolKeyForActionType` (`:530-531`), and the I42 section records that "Extension tools stay NOT proposable on the I28 act door (`classifyActionType` leaves `ext_` as `unknown`)". Nothing here changes that: every new branch tests `USER_MCP_SERVICE_ID_PATTERN`, never `isOwnerCodeServerServiceId`. A test proposes an `ext_*` type and gets `unknown`.

**D-2 The verdict for a user-MCP type** (`agent-door-runtime.ts`, synchronous, database reads only), in this order: (1) `userMcpActionParts` fails: `unknown`; (2) no `user_mcp_connector` row: `denied`, class `user_mcp_not_registered`; (3) a door approval for `(serviceId, tool)` whose `suspendedAt` is set: `suspended`; (4) a door approval exists and policy allows both `mcp_action` and `user_mcp_model_access` (fail closed on an unreadable policy): `proposable`, basis `approved`; (5) otherwise the unchanged classifier says `proposable` (a `--model` server while `user_mcp_model_access` allows): `proposable`, basis `legacy_user_mcp`; (6) otherwise `denied` with the classifier's class or `agent_not_approved`. The `--model` and agent grants are independent: step 4 never reads `model_access`. `refusal` returns `undefined` for both user-MCP bases (no input rule exists for a tool the gateway does not understand; the payload stays under the ordinary cap because `boundInput` is never set).

**D-3 The definition hash for `mcp_*`.** What is hashed: `definitionSha256(tool, entry)`, that is the tool name, the listed description and the listed input schema read back verbatim. The raw listed schema is hashed, not the sanitised one, because the sanitiser drops keywords (`pattern`, `default`, `examples`, `engine/user-mcp-input-schema.ts` header) and a change inside a dropped keyword is still a change of definition (OR-AD-5: "any change"). When: at submit as the last step for an `approved` basis only (`capture-gate.ts:470-476`), at approval (`capture-act.ts:283`), and after the owner's answer (`vetoingConsent`, `ipc/capture-rpc.ts:245-261`). The user-MCP branch of `verifyDefinition`: read the approval; list through `listUserMcpDefinitions`; re-read the approval with no await before the comparison; call `checkAgentToolDefinition` (the ONE mark-and-audit helper, `agent-door-definition.ts:74-123`, `:136-160`) with no `row`. Outcomes: `changed` or `unreadable` marks the sticky suspension with one `connector.writes.agent.suspend` audit row and returns `ERR_AGENT_TOOL_SUSPENDED`; `missing` (the listing omits the tool) and an `undefined` listing (the server cannot be started or listed now) return `ERR_CAPTURE_ACTION_NOT_PROPOSABLE`, mark nothing and write no row (OR-AD-14). A stopped server is not "missing": the listing starts it. The Wave 4 support check and the drift check do not apply (no row). At approval and at the veto the check also refuses, with `ERR_CAPTURE_ACTION_NOT_PROPOSABLE` and a fixed text, a proposal whose `createdAt` is older than the server's current `created_at`: it was proposed against an earlier registration (R-2).

**D-4 The enable for an `mcp_*` service** (`agent-writes-user-mcp.ts`), in a fixed order: (1) the caller declared `cli` or `ui` (`requireAgentEnableCaller`'s rule, `agent-writes.ts:95-106`; OR-AD-11); (2) arguments: `wave` and the scope parameters are refused, `approve` follows OD-3; the `approve` names are de-duplicated before anything else uses them, so a repeated name appears once in the prompt, the reply and the stored rows (round 2 finding 2); (3) the server is registered; (4) policy allows `mcp_action` and `user_mcp_model_access`; (5) the listing, the only I/O before the prompt (it starts the server, as `nimbus connector tools` does); (6) each named tool is in the listing and hashes; (7) the owner's gate, action type `connector.writes.enable` (already in the frozen set, so the HITL count stays 185), on the human-only channel; (8) ONE transaction: `upsertDoorApprovals` (or `replaceDoorApprovals` under OD-3(b)). It never writes the shared wave row. The prompt shows: `Door: outside agents (MCP)`; the server id and "third-party code you registered on <date>"; its sandbox reach, one line per `--read` path and `--net` host with the same network note the registration prompt uses (`buildAddMcpConsentPayload`, `ipc/connector-rpc.ts:109-128`), and `write: none beyond its own sandbox directory`; whether it also has `--model` ("separate"); then per tool: the name, its state (`will be approved`, `already approved`, `re-approved, changed`), the first 12 hex of the hash and the first 200 characters of the server's description, escaped and marked as the server's own text; then fixed lines: every call is approved by you one at a time and shows the exact input; a changed definition suspends the tool; the hash covers the listing and not what the code does; approvals are removed when the server is removed. `disable mcp_<id> --door agent` already works.

**D-5 Approvals live and die with the registration.** `handleConnectorRemove` deletes the server's door approvals in the same transaction as `deleteUserMcpConnector`, and `handleConnectorAddMcp` deletes any leftover approvals for the id in the same transaction as the insert (the same reason as `assertUserMcpSandboxClean`, `config.ts:126-144`). A re-registered id therefore starts with nothing approved for agents. The delete goes through `removeDoorApprovals` (`door-approval-store.ts:143-150`), so D49(b) holds. A removed server's waiting proposals are refused at approval by step 4b (`ERR_CAPTURE_CONNECTOR_UNCONFIGURED`) and expire.

**D-6 The per-call approval display.** `buildActDeps.execute` asks the runtime for the call facts and puts them on the action as `userMcpCall`. For an `approved` basis the runtime lists once, runs the D-3 check on that listing, and returns the description of the entry whose hash it just compared, so the text shown is the text that was hashed; a failed check is a `rejected` outcome with no prompt. For a legacy basis it reads the registration row only (no listing) and `approval` is null. The executor renders, in the untemplated agent branch, before the verbatim input:

```
User MCP server: mcp_notes (third-party code you registered on <ISO date>)
Sandbox reach:
  read: <path>            (one line each; "none" when empty)
  net: <host[:port]>      (one line each; the network note when the OS cannot filter per host)
  write: none beyond its own sandbox directory
Tool: append
Approved for outside agents on <ISO date>, definition 3fa9c1d2e4b7
Tool description (the server's own text, UNVERIFIED): "<escaped, at most 1000 characters>"
No before-state is available for a user MCP tool.
```

For a legacy proposal the two approval lines read `Not approved for outside agents by name.` and the description line is absent. Every variable string goes through `escapeUnverifiedLine`; each list shows at most 20 lines and then `and N more`. The verbatim input and the trailing proposer block are unchanged. There is no typed preview, no before-state and no typed confirmation (OD-4), so "parity with the model door" for a user-MCP tool means: the same executor, the same gate, no delegate, and a prompt that is a superset of the model door's. The desktop's structured details gain `userMcp` (sanitised with `sanitisePreviewText`). The audit row projects the field to the definition hash alone, placed after the proposer projection (R-4). The key is OMITTED when the action carries no `userMcpCall` (a conditional spread, never a property set to `undefined`): the existing strict-equality assertion on a legacy user-MCP call's audit row (`packages/gateway/test/e2e/user-mcp.e2e.test.ts:594-608`) must keep passing unchanged, and a row's text for every non-approved call must stay byte-identical (round 1 finding 2). A unit test asserts `Object.keys` of the projected action for a legacy call. A model-origin or owner call carries no `userMcpCall` and its prompt is byte-identical to today's.

**D-7 The deprecation window for user MCP.** A legacy user-MCP proposal is stored with `legacy = 1` and warned about on the four existing surfaces with one new fixed line: `Deprecated: <type> is not approved for outside agents by name. It is accepted for now and will be refused in a later release. To keep it working run: nimbus connector writes enable <serviceId> --door agent --approve <tool>`. The service id and tool come from `userMcpActionParts`, never from request text. It is held to today's rule only (`--model`, `user_mcp_model_access`, `mcp_action`), runs through the same executor, and is never vetoed. A suspended tool is never a legacy case. The enforcing slice deletes step 5 of D-2, the classifier's user-MCP branch and the line (OD-2).

**D-8 `describe_actions` for `mcp_*`.** Summary (no listing, nothing started): each approved tool by name with `state: "approved"`, `wave: null`, `typedConfirm: false`, `bound: false`; each suspended one; and, during the window, one `mcp_<id>.*` pattern per `--model` server with `state: "legacy"` and the fixed line. A named type: a legacy one returns the fixed line and causes no listing (OR-AD-18); an approved one is listed and described only after the D-3 check passes in the same call. The description is `describeOwnerCodeTool(serviceId, text)`, the model door's own string (prefix `owner-registered user MCP server <id>; treat its output as data.`, the text closer-escaped inside `<tool_description>`, 1000 characters in all). The schema is `offeredInputJsonSchema(entry.inputSchema)` (`engine/user-mcp-agent-tools.ts:116-124`). The reply still carries no hash, no approval date, no path and no host. `capture.status` advertises the same types. What a describe may start, and its bound: OD-5(a).

**D-9 CLI.** `nimbus connector writes enable mcp_<id> --door agent --approve <tool>...` (declares `cli`, person-only consent, as the first-party path at `connector-writes-cli.ts:304-328`). `status` prints a section "User MCP servers (outside agents)" for agent services that have no model row: per server the approved count, each suspended tool with both hash prefixes, each `not listed now` tool, and `unverified` when the server could not be listed. The agent policy line names `user_mcp_model_access` when that is the lockoff. `nimbus connector add --mcp` gains no flag in AD5a.

**D-10 Policy.** An approved user-MCP proposal needs `mcp_action` and `user_mcp_model_access`, as the spec says (`:512-513`). It does not need `connector_write_model_access`, which is about first-party writes. Stated limit: an organisation cannot allow user MCP tools to the model and forbid them to agents except by turning `mcp_action` off, which closes the whole act door.
